# TBot 3.5.1-beta2g

Fixes a login loop when opening OGame support through the local game proxy. An HTTP 302/303 redirect to the official support SSO endpoint was treated as a lost game session. Repeated login attempts could hold the shared ogamed queue, causing resource, fleet and Defender reads to time out in TBot.

The backend now returns the expected browser-side navigation for GET `page=ingame&component=support` redirects to HTTPS `ogame.support.gameforge.com/index.php`. It does not follow the SSO destination server-side or trigger another login. The URL is encoded safely for JavaScript and fallback HTML, and accepted redirects do not log their SSO key. Existing 200/script responses remain supported. Real session redirects, other destinations and state-changing fleet/discovery retry rules retain their previous behavior.

All changes from **3.5.1-beta2f** remain included, including configurable manual-mode inactivity timeout, expedition primary/secondary sharing, conservative fleet-send reconciliation and highscore navigation. No settings change is required.

Validation before publication: 24 new offline Go cases cover accepted redirects, exact URL preservation/escaping, session and queue state, manual transactions, legacy responses, and rejected methods, routes and URLs. The original reproduction failed before the fix. Full Go tests and `go build ./...`, all **615 C# tests**, **15 release-policy tests**, and **20 local preparation/guard tests** passed. Existing C# compiler/dependency warnings remain unchanged. Release CI repeats the full checks and builds seven platform packages; publication follows archive provenance and SHA256 verification.

This fixes an offline-reproduced defect. The historical incident log recorded support HTTP 302 and repeated login attempts, but not its exact Location header. No live login, support SSO, or fleet dispatch was used for validation. The pinned Go fix is `d0f8e6014b1c05e1ae5cdb61f3d5ee1d6edb19f2`. Exact TBot and Go commits are included in every package's `BUILD-INFO.txt`.

Prepare the new installation alongside the previous client. Stop the old client before manually starting the new one. The local first-start launcher imports final old-client state once after shutdown and refuses changed old settings; neither program is started during preparation.
